# 成员名册由客户联系 API 轮询同步，退群即删

日期：2026-09-12

## 背景

会话存档消息只含 userid，@回复需要显示名。scope 定稿（功能 21）原本把 accessToken 用途限定为"未知 userid 懒查昵称"。用户在 P1 设计拷问中明确要求：新人入群自动更新名册，成员退群直接删除其名册行。

## Decision

- 名册主键为 `(roomid, userid)` 复合键（同一人在不同群可有不同群昵称）。
- 同步以客户联系 API `groupchat/get?need_name=1` 返回的成员全集为唯一权威：
  1. 进程启动对 room_map 启用群全量同步一次；
  2. 守护线程每 5 分钟对每群拉取一次并做 diff；
  3. 存档处理中遇到未知 (roomid,userid) 时立即刷新该群，不等轮询周期。
- 每群的 insert/update/delete 在单个 SQLite 事务内原子完成：在 API 集合中即新增/更新；不在即硬删除（manual_override 行也不保留）。
- 手工改名 `manual_override=1` 的行，其 display_name 不被同步覆盖（但人退群仍删除整行）。
- 即时刷新后仍查不到的 userid 落 pending（待补录）行，出站降级为不带 @ 的纯文本。
- accessToken 仅存内存缓存（到期前 5 分钟刷新），不入库；qyapi 直连。

## Alternatives Considered

- **严格懒查（scope 原案）**：不说话的新人永远不会入库，无法满足"入群自动更新"，且无法感知退群。否决。
- **客户群变更事件回调**：需要公网可达的回调服务与验签，违反单进程/内网自用形态。否决。
- **存档 SDK event 消息感知入群**：依赖外部联系人同意存档，覆盖面不保证。否决。

## Consequences

- accessToken 用途从"懒查"扩展为"名册全量/轮询同步"，构成对 scope 功能 21 的有意扩展（已记入 scope 第四节）。
- 3 群 × 每 5 分钟 ≈ 日 864 次调用，远低于客户联系 API 限额；调用量随群数线性增长，群数量显著增加时需重新评估周期。
- API 故障期间名册保持上次同步结果，不阻断监听与回复主流程。
